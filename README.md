# Практическая работа: безопасный удалённый доступ по SSH на Альт Сервер

В этой работе вы создадите две виртуальные машины с ОС «Альт Сервер» в VMware Workstation и настроите на них безопасный удалённый доступ.

Машины называются так же, как серверы в экзаменационной схеме:

~~~text
HQ-SRV  — сервер головного офиса
BR-SRV  — сервер филиала
~~~

На каждом сервере нужно выполнить три задания:

1. создать локального пользователя `sshuser`;
2. настроить SSH так, чтобы подключаться можно было только безопасным способом, которого требует задание;
3. установить правильный часовой пояс.

В конце работы:

~~~text
ssh -p 2026 sshuser@<IP сервера>
~~~

должна подключать вас к серверу с баннером `Authorized access only`, а любые другие попытки входа (по порту 22, под root, под другим пользователем, с тремя неверными паролями) должны отклоняться.

Работа рассчитана на дистрибутив **«Альт Сервер» 10.x или 11.x** (именно дистрибутив, а не сборочное окружение). Если преподаватель выдал другую близкую редакцию Альт, названия отдельных пунктов установщика могут немного отличаться, но команды остаются теми же.

> В примерах ниже используются адреса 192.168.100.128 и 192.168.100.129. У вас VMware почти наверняка выдаст другие адреса. Не копируйте примерные IP вслепую: сначала выполните шаг 5 и запишите свои значения.

## Что мы создаём

Для работы нужны две виртуальные машины. У каждой будет только один сетевой адаптер в режиме NAT.

~~~text
                         Интернет
                            │
                            │
                     VMware NAT
                            │
              ┌─────────────┴─────────────┐
              │                           │
              ▼                           ▼
┌────────────────────────┐   ┌────────────────────────┐
│ Альт Сервер №1         │   │ Альт Сервер №2         │
│                        │   │                        │
│ HQ-SRV                 │   │ BR-SRV                 │
│ sshd, порт 2026        │   │ sshd, порт 2026        │
│ пользователь sshuser   │   │ пользователь sshuser   │
└────────────────────────┘   └────────────────────────┘
~~~

Обе виртуальные машины находятся в одной NAT-сети VMware. Поэтому они:

- получают доступ в интернет;
- получают IP-адреса от DHCP VMware;
- могут обращаться друг к другу по IP-адресам.

Подключаться по SSH мы будем с одного сервера на другой: с BR-SRV на HQ-SRV и наоборот. Отдельный клиент не нужен.

Для этой работы:

- не нужен второй сетевой адаптер;
- не нужен Host-only;
- не нужно открывать Virtual Network Editor;
- не нужен пароль администратора Windows.

## Что такое SSH

SSH (Secure Shell) — протокол удалённого управления. Он позволяет открыть консоль другого компьютера по сети, при этом весь трафик, включая пароль, шифруется.

Схема подключения:

~~~text
          ssh -p 2026 sshuser@192.168.100.128
BR-SRV ─────────────────────────────────────────▶ HQ-SRV
                                                   sshd слушает порт 2026
~~~

Серверная часть называется `sshd`. Её настройки лежат в файле:

~~~text
/etc/openssh/sshd_config
~~~

> В Ubuntu этот файл находится в `/etc/ssh/`. В Альт каталог называется `/etc/openssh/`. Это одно из самых частых отличий.

По умолчанию SSH слушает порт 22, пускает любого пользователя системы и даёт несколько попыток ввести пароль. Именно эти настройки мы и ужесточим.

## Требования задания

### Задание 3. Локальные учётные записи на HQ-SRV и BR-SRV

- создать пользователя `sshuser`;
- пароль пользователя: `P@ssw0rd`;
- идентификатор пользователя (UID): `2026`;
- `sshuser` должен запускать `sudo` без ввода пароля.

### Задание 5. Безопасный удалённый доступ на HQ-SRV и BR-SRV

- для подключения использовать порт `2026`;
- разрешить подключения исключительно пользователю `sshuser`;
- ограничить количество попыток входа до двух;
- настроить баннер `Authorized access only`.

### Задание 11. Часовой пояс

- настроить часовой пояс на всех устройствах согласно месту проведения экзамена.

> Задание про пользователя `net_admin` относится к маршрутизаторам HQ-RTR и BR-RTR. В этой работе маршрутизаторов нет, поэтому `net_admin` не создаётся.

## Что нужно запомнить перед началом

С шага 5 и до конца работы обе виртуальные машины должны быть запущены одновременно.

После шага 5 вы запишете два значения:

~~~text
IP HQ-SRV
IP BR-SRV
~~~

В примерах будет использоваться:

~~~text
HQ-SRV: 192.168.100.128
BR-SRV: 192.168.100.129
~~~

У вас адреса будут другими.

Если в инструкции написано:

~~~text
192.168.100.128
~~~

подставляйте IP своего HQ-SRV.

Если написано:

~~~text
192.168.100.129
~~~

подставляйте IP своего BR-SRV.

После того как вы записали адреса, не перезагружайте виртуальные машины без необходимости до окончания работы. DHCP VMware может выдать другой IP.

Ещё три правила, которые сэкономят время:

- Команды в этой работе выполняются от имени **root**. В Альт для этого после входа выполните `su -` и введите пароль root.
- Пока вы не убедились, что новый SSH работает, **не закрывайте консоль VMware** той машины, которую настраиваете. Если вы ошибётесь в конфигурации, через консоль VMware вы всегда сможете всё исправить.
- В Альт для установки пакетов используется `apt-get`, а не `apt`.

Должны быть ответы без потерь.

## Шаг 6. Создайте пользователя sshuser

**Где выполняем:** HQ-SRV, затем BR-SRV. Команды выполняются от root.

Если вы вошли обычным пользователем, станьте root:

~~~bash
su -
~~~

Создайте пользователя с нужным UID, домашним каталогом и оболочкой bash:

~~~bash
useradd -m -u 2026 -s /bin/bash sshuser
~~~

Разбор команды:

| Часть | Значение |
|---|---|
| `-m` | создать домашний каталог `/home/sshuser` |
| `-u 2026` | идентификатор пользователя 2026 |
| `-s /bin/bash` | оболочка по умолчанию |

Задайте пароль:

~~~bash
echo 'sshuser:P@ssw0rd' | chpasswd
~~~

Пароль нужно писать в одинарных кавычках. Так оболочка не будет пытаться толковать символы в пароле.

Проверьте:

~~~bash
id sshuser
~~~

Ожидаемый результат:

~~~text
uid=2026(sshuser) gid=... groups=...
~~~

Главное, чтобы после `uid=` стояло именно `2026`.

> Если в сообщении `UID 2026 is not unique`, значит идентификатор уже занят. Выполните `getent passwd 2026`, посмотрите, какой пользователь его занимает,. Если это не ваш `sshuser`, освободите UID или обратитесь к преподавателю.

## Шаг 7. Разрешите sshuser запускать sudo без пароля

**Где выполняем:** HQ-SRV, затем BR-SRV. От root.

В Альт пакет `sudo` может быть не установлен, а если установлен, по умолчанию он разрешён только группе `wheel`. Поэтому нужны три действия.

### 1. Установите sudo

~~~bash
apt-get update
apt-get install -y sudo
~~~

Если пакет уже есть, apt-get сообщит, что он установлен и обновлять его не нужно.

### 2. Добавьте sshuser в группу wheel

~~~bash
usermod -aG wheel sshuser
~~~

Проверьте режим работы sudo:

~~~bash
control sudo
~~~

Если ответ `public`, sudo доступен всем. Если `wheelonly`, то только группе wheel. Для задания подходит любой из них, потому что `sshuser` уже в группе wheel.

> Если вы видите `restricted` или `disabled`, включите режим для группы wheel: `control sudo wheelonly`.

### 3. Отключите запрос пароля для sshuser

Не редактируйте основной `/etc/sudoers` вручную. Создайте отдельный файл:

~~~bash
echo 'sshuser ALL=(ALL:ALL) NOPASSWD: ALL' > /etc/sudoers.d/sshuser
chmod 440 /etc/sudoers.d/sshuser
~~~

Проверьте синтаксис:

~~~bash
visudo -c
~~~

Ожидаемый результат — слова `parsed OK` для основного файла и файла `/etc/sudoers.d/sshuser`.

> Ошибка в sudoers может закрыть доступ к sudo для всех. Поэтому всегда проверяйте `visudo -c`. Если проверка нашла ошибку, исправьте или удалите файл `/etc/sudoers.d/sshuser` и повторите.

### Проверьте sudo без пароля

~~~bash
su - sshuser -c 'sudo -n id'
~~~

Ожидаемый результат:

~~~text
uid=0(root) gid=0(root) groups=0(root)
~~~

Ключ `-n` запрещает sudo спрашивать пароль. Если пароль требуется, команда завершится ошибкой, и это значит, что настройка не работает.

## Шаг 8. Проверьте SSH-сервер до настройки

**Где выполняем:** HQ-SRV. От root.

Сначала посмотрите, как работает SSH сейчас.

~~~bash
systemctl status sshd --no-pager
~~~

Должно быть `active (running)`.

Если ответ `Unit sshd.service could not be found`, установите сервер:

~~~bash
apt-get install -y openssh-server
systemctl enable --now sshd
~~~

Включите автозапуск, чтобы SSH работал после перезагрузки:

~~~bash
systemctl enable --now sshd
~~~

Посмотрите, какой порт слушается:

~~~bash
ss -lntp | grep sshd
~~~

Сейчас должно быть что-то вроде:

~~~text
LISTEN 0 128 0.0.0.0:22 ... users:(("sshd",...))
~~~

Это порт 22. После настройки здесь должен остаться только порт 2026.

Посмотрите текущие значения нужных нам настроек:

~~~bash
sshd -T | grep -Ei '^(port|maxauthtries|allowusers|banner|permitrootlogin)'
~~~

Запомните их или сделайте снимок экрана. После шага 11 сравните.

## Шаг 9. Создайте баннер

**Где выполняем:** HQ-SRV, затем BR-SRV. От root.

Баннер — текст, который SSH показывает сразу после соединения, до ввода пароля.

Создайте файл баннера:

~~~bash
echo 'Authorized access only' > /etc/openssh/banner
~~~

Проверьте:

~~~bash
cat /etc/openssh/banner
~~~

Должна вывестись строка:

~~~text
Authorized access only
~~~

> Текст должен совпадать точно: с большой A в начале, без точки в конце и без лишних кавычек. Проверка может сравнивать строку буква в букву.

## Шаг 10. Настройте sshd

**Где выполняем:** HQ-SRV, затем BR-SRV. От root.

Сначала сделайте резервную копию:

~~~bash
cp /etc/openssh/sshd_config /etc/openssh/sshd_config.bak
~~~

В SSH действует правило: если директива встречается в файле несколько раз, берётся **первое** значение. Поэтому нельзя просто дописать `Port 2026` в конец файла: выше может быть уже активная строка `Port 22`. Сначала закомментируем старые строки этих четырёх директив:

~~~bash
sed -i -E 's/^[[:space:]]*(Port|AllowUsers|MaxAuthTries|Banner)[[:space:]]/#&/' /etc/openssh/sshd_config
~~~

Затем допишем свои настройки в конец файла:

~~~bash
cat >> /etc/openssh/sshd_config <<'EOF'

# --- Практическая работа: безопасный SSH ---
Port 2026
AllowUsers sshuser
MaxAuthTries 2
Banner /etc/openssh/banner
EOF
~~~

Что означает каждая строка:

| Директива | Значение |
|---|---|
| `Port 2026` | sshd слушает порт 2026 вместо 22 |
| `AllowUsers sshuser` | подключаться может только пользователь sshuser, остальным (включая root) отказ |
| `MaxAuthTries 2` | не больше двух неудачных попыток входа за одно соединение |
| `Banner /etc/openssh/banner` | показывать содержимое файла как баннер |

Посмотрите конец файла:

~~~bash
tail -n 8 /etc/openssh/sshd_config
~~~

> Если у вас в системе есть каталог `/etc/openssh/sshd_config.d/` с файлами настроек, они могут переопределять наши директивы. Итоговую проверку на шаге 11 выполняйте командой `sshd -T`: она показывает значения, которые sshd применит на самом деле.

## Шаг 11. Проверьте конфигурацию и перезапустите sshd

**Где выполняем:** HQ-SRV. От root.

### Проверка синтаксиса

~~~bash
sshd -t
~~~

Если команда ничего не вывела, ошибок нет. Если вывела сообщение, исправьте файл и повторите проверку. Перезапускать sshd с ошибкой нельзя.

### Просмотр применяемых значений

~~~bash
sshd -T | grep -Ei '^(port|maxauthtries|allowusers|banner)'
~~~

Ожидаемый результат:

~~~text
port 2026
maxauthtries 2
allowusers sshuser
banner /etc/openssh/banner
~~~

### Перезапуск

~~~bash
systemctl restart sshd
systemctl is-active sshd
~~~

Ожидаемый ответ:

~~~text
active
~~~

### Проверка порта

~~~bash
ss -lntp | grep sshd
~~~

Должен остаться порт `2026`, а порта `22` быть не должно.

> Не закрывайте консоль VMware до окончания шага 12. Если sshd не запустился, вы исправите конфигурацию через консоль.

## Шаг 13. Проверьте запреты

**Где выполняем:** BR-SRV, подключаясь к HQ-SRV.

Настройка безопасности считается рабочей, только если лишнее реально запрещено.

### Порт 22 закрыт

~~~bash
ssh -p 22 sshuser@192.168.100.128
~~~

Ожидаемо:

~~~text
ssh: connect to host 192.168.100.128 port 22: Connection refused
~~~

### Root не может подключиться

~~~bash
ssh -p 2026 root@192.168.100.128
~~~

Баннер появится, и SSH спросит пароль. Даже с правильным паролем root результат будет:

~~~text
Permission denied, please try again.
~~~

Так происходит из-за `AllowUsers sshuser`: любой, кроме sshuser, отклоняется.

Нажмите Ctrl+C, если SSH продолжает спрашивать пароль.

### Другой пользователь не может подключиться

Если у вас на HQ-SRV есть другой обычный пользователь (например, `student`), проверьте и его:

~~~bash
ssh -p 2026 student@192.168.100.128
~~~

Ожидаемо: отказ.

### Три неверных пароля

~~~bash
ssh -p 2026 -o PubkeyAuthentication=no sshuser@192.168.100.128
~~~

Введите неверный пароль. Затем ещё раз неверный.

Обычный клиент SSH даёт три попытки. Сервер с `MaxAuthTries 2` обрывает соединение уже после второй ошибки, и третьего запроса пароля вы не увидите. Ожидаемое сообщение:

~~~text
Received disconnect from 192.168.100.128 port 2026:2: Too many authentication failures
~~~

или

~~~text
Connection closed by 192.168.100.128 port 2026
~~~

Текст зависит от версии клиента. Главное — сервер закрыл соединение после двух неудач.

> Параметр `-o PubkeyAuthentication=no` отключает попытки входа по ключам. Иначе ключи из ssh-agent тоже считаются попытками и попытки закончатся раньше, чем вы введёте пароль.

### Посмотрите журнал на HQ-SRV

На HQ-SRV выполните:

~~~bash
journalctl -u sshd --no-pager -n 30
~~~

Вы увидите попытки входа, отказ для root и сообщение о превышении числа попыток. Для студента это очень полезная практика: читать журнал, чтобы понять, почему вход не удался.

## Шаг 14. Настройте часовой пояс

**Где выполняем:** HQ-SRV, затем BR-SRV. От root.

Посмотрите текущие настройки:

~~~bash
timedatectl
~~~

В строке `Time zone` указан текущий пояс.

Найдите нужный часовой пояс. Например, для России:

~~~bash
timedatectl list-timezones | grep -i Europe/
~~~

Укажите часовой пояс места проведения экзамена. Название формата `Регион/Город`. Узнайте у преподавателя, какой пояс нужен. Для примера возьмём Москву:

~~~bash
timedatectl set-timezone Europe/Moscow
~~~

Подставьте свой город, если пояс другой, например:

| Город | Значение |
|---|---|
| Москва | `Europe/Moscow` |
| Екатеринбург | `Asia/Yekaterinburg` |
| Омск | `Asia/Omsk` |
| Новосибирск | `Asia/Novosibirsk` |
| Владивосток | `Asia/Vladivostok` |

Проверьте:

~~~bash
timedatectl
date
~~~

Ожидаемо:

~~~text
Time zone: Europe/Moscow (MSK, +0300)
~~~

Время в строке `date` должно совпадать с вашим местным временем. Если оно отстаёт или спешит на несколько часов, проверьте, что пояс выбран верно. Если расхождение в минутах, это обычная погрешность часов виртуальной машины, и для задания значения не имеет.

Выполните эту настройку на **обоих** серверах.

## Шаг 16. Выполните итоговую проверку

**Где выполняем:** HQ-SRV и BR-SRV, от root.

Выполните этот набор команд на каждом сервере:

~~~bash
hostname
id sshuser
su - sshuser -c 'sudo -n id'
cat /etc/openssh/banner
sshd -T | grep -Ei '^(port|maxauthtries|allowusers|banner)'
ss -lntp | grep sshd
systemctl is-enabled sshd
systemctl is-active sshd
timedatectl | grep 'Time zone'
~~~

Ожидаемые результаты:

| Проверка | Результат |
|---|---|
| `hostname` | `hq-srv` или `br-srv` |
| `id sshuser` | `uid=2026(sshuser)` |
| `sudo -n id` | `uid=0(root)` без запроса пароля |
| баннер | `Authorized access only` |
| `sshd -T` | `port 2026`, `maxauthtries 2`, `allowusers sshuser`, `banner /etc/openssh/banner` |
| `ss` | слушается только порт 2026 |
| `is-enabled` | `enabled` |
| `is-active` | `active` |
| часовой пояс | ваш пояс, например `Europe/Moscow` |

Затем проверьте работу по сети с обеих сторон:

~~~bash
ssh -p 2026 sshuser@<IP другого сервера>
~~~

Перезагрузите один из серверов и убедитесь, что после загрузки SSH на порту 2026 работает без вашего вмешательства:

~~~bash
reboot
~~~

> Проверка перезагрузкой нужна, потому что настройка, которая сработала только до перезагрузки, на экзамене не засчитается. После перезагрузки IP может измениться. Узнайте его заново командой `ip -br -4 address`.

## Частые ошибки

### После перезапуска снова открывается установщик Альт

Причина: ISO всё ещё подключён как виртуальный CD/DVD.

Выключите виртуальную машину.

Откройте:

**VM → Settings → CD/DVD**

Снимите:

~~~text
Connect at power on
~~~

Запустите виртуальную машину снова.

### Сервер не отвечает на пинг от другого сервера

На обеих машинах выполните:

~~~bash
ip -br -4 address
~~~

Проверьте:

1. Обе машины запущены.
2. У обеих один Network Adapter.
3. У обеих выбран NAT.
4. Вы используете текущие IP-адреса.
5. Адрес 127.0.0.1 не используется для связи между машинами.

### `ssh: connect to host ... port 2026: Connection refused`

Причины и проверки на сервере:

1. sshd не запущен:

~~~bash
systemctl status sshd --no-pager
~~~

2. sshd слушает не тот порт:

~~~bash
ss -lntp | grep sshd
~~~

3. Вы не перезапустили sshd после изменения конфигурации:

~~~bash
systemctl restart sshd
~~~

4. Брандмауэр блокирует порт. Посмотрите правила:

~~~bash
iptables -S
nft list ruleset
~~~

В учебной установке Альт правил обычно нет. Если они есть, нужно разрешить TCP-порт 2026.

### `ssh: connect to host ... port 2026: Connection timed out`

Причина: клиент вообще не достучался до сервера. Проверьте IP-адрес сервера. Возможно, после перезагрузки DHCP выдал другой адрес.

### `sshd -t` выводит ошибку

Типичное сообщение:

~~~text
/etc/openssh/sshd_config line 118: Bad configuration option: ...
~~~

Откройте файл на указанной строке и исправьте опечатку. Директивы в sshd_config нужно писать без ошибок: `MaxAuthTries`, а не `MaxAuthTry`.

Если вы всё сломали, верните исходную конфигурацию и повторите шаг 10:

~~~bash
cp /etc/openssh/sshd_config.bak /etc/openssh/sshd_config
~~~

### `sshd -T` показывает `port 22`, хотя мы дописали `Port 2026`

Причина: выше в файле осталась активная строка `Port 22`, а SSH использует первое значение.

Найдите все строки:

~~~bash
grep -n -E '^\s*Port' /etc/openssh/sshd_config
~~~

Закомментируйте лишние и оставьте только `Port 2026`. Затем снова выполните `sshd -t` и `systemctl restart sshd`.

Также проверьте каталог дополнительных конфигураций:

~~~bash
grep -rn -E '^\s*(Port|AllowUsers|MaxAuthTries|Banner)' /etc/openssh/
~~~

### Баннер не отображается

Проверьте по порядку:

1. Файл существует и не пуст:

~~~bash
cat /etc/openssh/banner
~~~

2. Директива указана верно:

~~~bash
sshd -T | grep banner
~~~

Должно быть `banner /etc/openssh/banner`.

3. sshd перезапущен.
4. Вы подключаетесь к правильному серверу и порту.

Баннер показывается **до** запроса пароля, а не после входа. Не путайте его с файлом `/etc/motd`, который показывается уже после входа.

### `Permission denied` для sshuser при верном пароле

Проверьте:

1. Пароль задан без опечаток. Установите заново:

~~~bash
echo 'sshuser:P@ssw0rd' | chpasswd
~~~

2. В `AllowUsers` стоит `sshuser`, а не `sshuser ` с лишними символами или `ssuser`.
3. Раскладка клавиатуры: пароль содержит `@` и цифру 0.
4. Пользователь не заблокирован:

~~~bash
passwd -S sshuser
~~~

Состояние должно быть `P`, а не `L`.

Причину всегда видно в журнале:

~~~bash
journalctl -u sshd --no-pager -n 30
~~~

### sudo просит пароль

Проверьте:

~~~bash
cat /etc/sudoers.d/sshuser
visudo -c
id sshuser
control sudo
~~~

Должно быть:

- в файле строка `sshuser ALL=(ALL:ALL) NOPASSWD: ALL`;
- `visudo -c` говорит `parsed OK`;
- в `id` в списке групп есть `wheel`;
- `control sudo` показывает не `disabled`.

Если права на файл неверны, исправьте:

~~~bash
chmod 440 /etc/sudoers.d/sshuser
~~~

### `sudo: command not found`

Пакет `sudo` не установлен:

~~~bash
apt-get update
apt-get install -y sudo
~~~

### `E: Unable to locate package` или apt-get не видит репозитории

Проверьте интернет:

~~~bash
ping -c 4 8.8.8.8
ping -c 4 ya.ru
~~~

Если пинг до IP работает, а до имени нет, проблема в DNS. Если пинга нет вообще, проверьте NAT на шаге 1. После восстановления сети выполните:

~~~bash
apt-get update
~~~

### `useradd: UID 2026 is not unique`

Этот UID уже занят:

~~~bash
getent passwd 2026
~~~

Если это ваш ранее созданный `sshuser`, значит, пользователь уже есть и повторно создавать его не нужно: переходите к проверке `id sshuser`.

### Только две попытки ввода пароля, но клиент не отключается

Скорее всего, настройка не применилась. Проверьте:

~~~bash
sshd -T | grep maxauthtries
~~~

Должно быть `maxauthtries 2`. Затем перезапустите sshd.

### Соединение закрывается до того, как я ввёл пароль

Причина: клиент сначала пробует ключи из ssh-agent, и каждая попытка расходует лимит в две попытки. Подключайтесь так:

~~~bash
ssh -p 2026 -o PubkeyAuthentication=no sshuser@192.168.100.128
~~~

### Я закрыл консоль и больше не могу войти по SSH

Войдите в виртуальную машину через консоль VMware под root, проверьте `sshd -t`, статус службы `sshd` и порт. Если нужно, верните резервную копию `/etc/openssh/sshd_config.bak`.

### Предупреждение `REMOTE HOST IDENTIFICATION HAS CHANGED`

Причина: у IP-адреса теперь другой сервер или переустановлена система. Удалите старую запись и подключитесь заново:

~~~bash
ssh-keygen -R 192.168.100.128
~~~

Для порта, отличного от 22, запись хранится в виде `[IP]:2026`. Если команда выше не помогает:

~~~bash
ssh-keygen -R '[192.168.100.128]:2026'
~~~

### Часовой пояс установлен, но время неверное

Проверьте:

~~~bash
timedatectl
date
~~~

Если пояс верный, а время отличается на минуты, это погрешность часов ВМ. Если отличается на часы, значит, выбран не тот пояс. Задайте нужный:

~~~bash
timedatectl set-timezone Europe/Moscow
~~~

### `Failed to set time zone: Invalid time zone`

Опечатка в названии. Найдите правильное:

~~~bash
timedatectl list-timezones | grep -i moscow
~~~

Регистр важен: `Europe/Moscow`, а не `europe/moscow`.

## Что нужно понимать после выполнения

- SSH шифрует соединение, поэтому пароль не передаётся по сети открытым текстом.
- Серверная часть SSH называется sshd, а её конфигурация в Альт находится в `/etc/openssh/sshd_config`.
- Порт 22 используется по умолчанию, и именно его чаще всего сканируют злоумышленники. Смена порта не заменяет другие меры, но уменьшает шум в журналах.
- `AllowUsers` задаёт белый список: всё, чего нет в списке, запрещено.
- `MaxAuthTries` ограничивает число попыток входа на одно соединение. Полноценную защиту от перебора паролей это не даёт, но ограничивает его скорость.
- Баннер показывается до входа и обычно используется для юридического предупреждения.
- Если директива встречается в `sshd_config` несколько раз, действует первое значение.
- `sshd -t` проверяет конфигурацию, а `sshd -T` показывает значения, которые реально применяются.
- Перед перезапуском службы всегда нужно проверять конфигурацию и не закрывать запасной доступ (консоль VMware).
- Правило `NOPASSWD` в sudo удобно для автоматизации, но снижает безопасность. Его нужно выдавать осознанно.
- Файлы настроек sudo лучше класть в `/etc/sudoers.d/` и проверять командой `visudo -c`.
- В Альт управление правами `sudo` устроено через `control`, а пакеты ставятся командой `apt-get`.
- Часовой пояс нужен не только для красоты: от него зависят метки времени в журналах, расписания и сертификаты.
